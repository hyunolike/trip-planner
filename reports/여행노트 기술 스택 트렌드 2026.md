# 여행노트 2026 스택: 유행 대신 설명 가능한 결정을 고른다

네이버, 쿠팡, 우아한형제들, 카카오, 토스, 당근의 2025–2026년 채용 공고와 기술 블로그를 종합하면, 이 회사들이 사이드 프로젝트에서 보는 것은 특정 신기술의 유무가 아니라 **"왜 그 기술을 골랐고 대안은 왜 기각했는지"를 설명하는 능력, 테스트와 모니터링과 배포 자동화의 존재, 그리고 AI 도구 산출물을 통제한 증거**다. 토스는 이력서에 "문제의식, 가설, 해결 방식, 결과, 어려웠던 점"을 쓰라고 직접 안내하고([토스 Server Developer 공고](https://toss.im/career/job-detail?job_id=6288478003)), 당근은 "성능·비용·보안처럼 서로 충돌하는 요구 사이에서 근거를 갖고 결정을 내리고 설명해본 경험"을 자격요건으로 적었으며([당근 Identity Service 공고](https://careers.daangn.com/jobs/role/5046759003/)), 쿠팡의 2026년 10월 Staff 공고는 "명확한 경계, 강력한 계약, 포괄적인 테스트"와 함께 별도의 "AI & Harness Engineering" 섹션을 두었다([쿠팡 Staff Back-end 공고](https://www.dreamworkhq.com/job/ee6f6e1e-926b-460f-8188-bb144c1becdd)). 이 기준에 맞춰 여행노트가 2026년 10월 15일 시점에 반영해야 할 핵심 변경은 여덟 가지다. **Spring Boot 4.1.x + Java 25 + Kotlin 2.3**으로 기준선을 올리고 Spring Modulith 2.1의 이벤트 퍼블리케이션 레지스트리로 Kafka 없는 아웃박스를 구현한다. 유지보수가 멈춘 QueryDSL 대신 **Spring Data JPA + jOOQ 3.21**을 쓴다. **PostgreSQL 18**의 `uuidv7()`과 PostGIS `geography`를 스키마에 넣는다. **Next.js 16.4의 Cache Components**를 켜고 에디터는 TanStack Query v5의 persist와 paused mutation으로 오프라인을 다룬다. 카카오맵은 일본 지도를 제공하지 않으므로 **MapLibre GL JS 6 + Protomaps 타일(한국어 라벨)**로 동선 지도를 그린다. Spring Boot 4의 OpenTelemetry 스타터를 **Grafana Cloud Free와 Sentry Developer**에 직결하고 SLO 세 개를 README에 적는다. CI는 SHA 고정 액션, OIDC, Artifact Attestation으로 공급망 보안을 비용 0원에 갖춘다. 마지막으로 ADR, 포스트모템, `CLAUDE.md`로 "결정 근거"를 레포 안에 남긴다. 반대로 Kafka, Kubernetes, MSA, gRPC, CRDT 전면 도입, 동기화 엔진, 알림톡, Datadog, Temporal, AWS App Runner는 이 규모에서 과잉이거나 2026년 기준으로 낡은 선택이다. 월 운영 비용은 Vercel Pro $20, API 컨테이너 약 $9, Supabase Pro $25를 합쳐 **$55~75** 밴드에 들어온다. 검증하지 못한 항목으로는 네이버 본사와 쿠팡 프론트엔드의 2025–2026 공고 원문, Hibernate 7과 Jackson 3의 jsonb 매핑 호환, 개인 개발자의 카카오 비즈 앱 전환 가능 여부가 남아 있다.

## 여섯 회사는 스택 키워드보다 결정 근거와 운영 증거를 본다

공고 레벨의 백엔드 스택은 놀랄 만큼 수렴한다. 토스 Server Developer(Product)는 "Java, Kotlin, Spring Framework, JPA/Hibernate, Netty, Golang / MySQL, Oracle, Redis, MongoDB, Kafka, Elasticsearch, Grafana"를 나열하고 전형에 라이브 코딩을 넣었으며([토스 Server Developer Product](https://toss.im/career/job-detail?job_id=4076140003)), 당근페이 백엔드는 "Kotlin, Spring Boot, Spring Batch, JPA, gRPC / MySQL, Redis, Kafka / Grafana, Sentry, Datadog / AWS, Kubernetes, Argo CD, GitHub Actions"를 적었다([당근페이 Backend](https://careers.daangn.com/jobs/role/4511184003/)). 우아한형제들 배민공통서비스개발팀(2025-10-01 게시)은 "Java, Kotlin, Spring (MVC, WebFlux, Batch), JPA, Gradle, gRPC / AWS / MySQL, Elasticsearch, DynamoDB, Redis / Grafana, Prometheus, Loki, Pinpoint"를 스택으로 두고 우대에 "빌드·테스트·배포 자동화 경험"과 "시스템 모니터링 및 알림 구축 경험"을 넣었다([배민공통서비스 공고](https://zighang.com/recruitment/bfc89828-b8c5-491e-a2d9-baef444500e5)). 쿠팡은 "Cloud Native (AWS), MSA, Spring Boot, JPA, Elastic Stack, Docker, Kafka, Redis, MySQL, Cassandra"라는 한 줄을 거의 모든 공고에 고정해 쓴다([쿠팡 Eats Merchant 공고](https://builtin.com/job/senior-back-end-engineer-eats-merchant/7929628)). 네이버웹툰의 2026년 3월 라인망가 공고도 "Java/Kotlin & Spring 기반 서버 개발 경험"을 자격으로, "MySQL, Redis, OpenSearch, Kafka"와 "Kubernetes 환경에서 서비스를 배포하고 운영해본 경험"을 우대로 둔다([네이버웹툰 라인망가 BE 공고](https://www.bzpp.co.kr/biz/businessDetailView/BR260305A00042)).

여기서 여행노트에 중요한 세 가지 사실이 나온다. 첫째, **Kotlin은 토스와 당근에서 1순위 언어이고 배민, 카카오, 쿠팡, 네이버, 라인에서는 "Java 또는 Kotlin"으로 병기**되므로 Kotlin + Spring Boot 선택은 어느 회사에서도 불이익이 없다. 다만 쿠팡은 Java 우선이라 Kotlin을 고른 이유 한 줄은 준비해야 한다. 둘째, **PostgreSQL을 명시한 공고는 조사 범위에서 하나도 없고 전부 MySQL/MariaDB 계열**이다. 이는 PostgreSQL이 감점이라는 뜻이 아니라, 평가 축이 DB 종류가 아니라 "RDBMS 설계, 인덱스, 트랜잭션, 마이그레이션, 슬로우 쿼리 분석" 같은 운영 증거라는 뜻이다. 여기어때 백엔드 공고가 "JPA/Hibernate 등 ORM과 도메인 모델링 경험"과 "AWS(EKS, RDS, ElastiCache) 기반 인프라 설계·운영"을 묻는 방식도 같다([여기어때 Backend 공고](https://www.wanted.co.kr/wd/383046)). 셋째, **Kafka, Kubernetes, MSA, gRPC는 공고에 자주 나오지만 예외 없이 "대용량 트래픽"과 "서비스 간 통신" 맥락**이다. 1인 B2C 앱에 이 키워드를 넣으면 면접에서 "RabbitMQ나 Redis Pub/Sub 대비 Kafka를 고른 이유"와 "분산 환경의 데이터 일관성"을 묻고 대부분 "트렌드라서" 수준으로 답한다는 것이 커뮤니티의 반복되는 관찰이다([인프런 커뮤니티](https://www.inflearn.com/vi/community/questions/1742305/이것도-포트폴리오에-넣어야할까요)).

프론트엔드는 더 극적이다. **Next.js를 자격요건에 적은 대기업 공고는 조사 범위에서 하나도 없었다.** 토스는 자체 SSR 프레임워크와 React Native 프레임워크를 쓰고 "수백 대의 SSR 서버를 안정적으로 운영"한다고 말하며([토스 프론트엔드 챕터](https://www.rocketpunch.com/en/jobs/153161)), 당근 Frontend 공고는 "React를 활용하는 SSR 웹 서비스의 개발 경험"을 자격요건으로, 스택은 "React, TypeScript, TanStack Query, vanilla-extract, Vite, fastify와 react-dom/server 기반 Streaming SSR"로 적고 우대에 "Claude Code, Codex 같은 코딩 에이전트로 본인만의 AI 워크플로우를 만들어 일하시는 분"을 넣었다([당근 Frontend 커뮤니티 공고](https://careers.daangn.com/jobs/role/7689088003/)). 배민 운영도구개발팀은 "TypeScript, React, Vue.js, Jotai, Zustand, React Query, pnpm"을 나열한다([배민 운영도구 FE 공고](https://devision.co.kr/job/259)). 그러니 Next.js 자체는 "리뷰어가 아는 도구"일 뿐이고, 점수는 **SSR과 스트리밍과 캐싱과 번들 분할을 왜 이렇게 했는지 설명하는 데**서 난다. 네이버 FE News가 주관한 State of FE·JS Korea 2025(249명)에서 TypeScript 주 사용 74.7%, React 계속 사용 의향 94.38%, Next.js 사용률 73%, Zustand 긍정 85.08%였다는 수치는 이 선택들이 한국 시장에서 "기본값"임을 뒷받침한다([네이버 D2 State of FE·JS Korea 2025](https://d2.naver.com/news/1353647)).

평가 기준을 회사가 직접 밝힌 문장은 많지 않지만 방향은 일치한다. 야놀자 채용 프로세스 페이지는 포트폴리오에서 "어떤 임팩트를 만들었는지"와 "어떤 고민과 과정이 있었는지"를 보고, 코딩테스트는 "정답 여부만을 평가하는 것이 아니라" 접근 방식, 가독성과 구조, 엣지 케이스 처리를 본다고 명시한다([야놀자 채용 프로세스](https://careers.yanolja.co/ko/hiringprocess)). 배민 CS프로덕트실은 "테스트 프레임워크를 활용한 테스트 코드 작성 경험"을 우대가 아닌 자격요건에 넣었고([배민 CS프로덕트실 공고](https://www.wanted.co.kr/wd/254673)), 당근 광고 백엔드는 "코드 리뷰와 테스트 가능하고 이해하기 쉬운 코드 작성에 관심"과 우대 "간단한 백오피스 도구를 만들 수 있는 능력"을 적었다([당근 광고 백엔드 공고](https://www.bzpp.co.kr/biz/businessDetailView/BR260325A00153)). 토스의 2026년 2월 "Harness" 글은 "같은 모델, 같은 IDE를 쓰는데도 결과물의 차이는 극심합니다. 차이는 단 하나, 작업 전에 컨텍스트를 설계했느냐의 여부입니다"라고 썼고([toss.tech Harness](https://toss.tech/article/45519)), 2026년 9월 Toss Benchmark 글은 공개 리더보드와 실제 업무의 상관이 ρ +0.02에 불과하고 자체 도메인 평가는 ρ +0.71이었다고 보고했다([toss.tech Toss Benchmark](https://toss.tech/article/toss-benchmark)). 네이버 D2는 "나쁜 테스트 코드를 방치한 채로 테스트 커버리지만 올리는 것은 곰팡이 핀 벽 위에 벽지를 바르는 것"이라고 썼고([D2 험블 객체 패턴](https://d2.naver.com/helloworld/9921217)), 통합검색의 "LCP p95 2.5초 이하"라는 구체 목표치를 공개했다([D2 AIB 도입과 웹 성능](https://d2.naver.com/helloworld/4241703)).

AI에 대한 기대치는 2025년 하반기부터 공고 문구로 굳었다. 카카오 2026년도 그룹 신입 공채는 "AI 네이티브 인재 선발에 초점"을 명시했고([카카오 2026 신입 공채](https://www.kakaocorp.com/page/detail/11688)), 당근 인프라 백엔드는 "AI 도구를 적극적으로 활용해 만들고 검증하는 속도를 높이고 계신 분"을 자격요건으로, 팀 문화로 "AI 컨텍스트를 저장소에 적용하고, 코드리뷰에 AI를 활용"한다고 적었다([당근 인프라 Backend](https://careers.daangn.com/jobs/role/7644271003/)). 쿠팡 Staff 공고는 AI 도구 사용을 "구현, 테스트, 코드 리뷰, 문서화" 네 영역으로 쪼개 묻고 "측정 가능한 생산성 향상 실적"을 요구한다([쿠팡 Staff Back-end 공고](https://www.dreamworkhq.com/job/ee6f6e1e-926b-460f-8188-bb144c1becdd)). 그런데 같은 회사들의 블로그는 AI 사용 자체가 아니라 **통제의 증거**를 강조한다. 배민 전자계약서 개편기는 Claude Code로 구현 속도가 약 2배, 테스트 코드가 약 8.5배 늘었지만 출시 후 2주간 버그가 4건(이전 2건)이었다고 솔직하게 적으면서 "코드가 나오는 속도보다 사람이 그 코드를 이해하는 속도가 먼저 한계에 닿았습니다"라고 결론지었다([배민 전자계약서 개편기](https://techblog.woowahan.com/27604/)). 배민 ArchUnit 글은 "규칙은 리뷰가 아닌 코드 레벨에서 지켜야 한다"며 팀 규칙을 `.claude/rules/`로 관리하고 테스트로 강제했지만, 동시에 "작은 단일 모듈 프로젝트는 설정이 노력 대비 가치가 없을 수 있다"고 경고했다([배민 ArchUnit 글](https://techblog.woowahan.com/26835/)). 네이버 AI 해커톤 1위 팀 후기는 "로컬 테스트 데이터만 지우기 위해 만든 초기화 코드가 공용 개발 데이터베이스에 연결된 상태에서 실행"된 사고를 공개하며 "무엇을 AI에게 맡기고, 무엇은 끝까지 맡기지 않을 것인가"를 핵심 질문으로 꼽았다([D2 AI 해커톤 후기](https://d2.naver.com/helloworld/4821538)). 여기어때는 "사람의 검토 없이 AI가 작성한 결과물을 그대로 올리는 것에 시니어가 불만"이 있고 그 원인이 "결정이 각자의 AI 대화 안에서 일어나기 때문"이라고 진단했다([여기어때 AI 시대 팀](https://techblog.gccompany.co.kr/ai-%EC%8B%9C%EB%8C%80-%EB%8B%B9%EC%8B%A0%EC%9D%98-%ED%8C%80-%EC%A1%B0%EC%A7%81%EC%9D%80-%EC%95%88%EB%85%95%ED%95%98%EC%8B%A0%EA%B0%80%EC%9A%94-c59f982d5add)).

회사 스스로가 과잉 설계를 경계하는 증거도 있다. 배민은 2026년 9월 워크플로 엔진으로 Temporal 도입을 "학습 곡선, 별도 인프라 운영, 엔진 디버깅 난이도, 벤더 락인"을 이유로 보류하고 필요한 개념 네 개만 자체 구현했다([배민 배치→워크플로](https://techblog.woowahan.com/26832/)). 당근 인프라 공고는 "기술은 문제를 해결하는 수단이라고 생각해요"와 "레거시 시스템과 과거의 선택을 존중"을 나란히 적었다([당근 인프라 Backend](https://careers.daangn.com/jobs/role/7644271003/)). 우아콘 2025에서 박경태 서버그룹 기술이사는 AI가 "생산성을 50%, 100% 높일 것이라는 외부 기대"와 달리 현장은 그만큼 체감하지 못했고 "의무감"으로 불필요한 곳에 AI를 쓰는 비효율이 있었다고 말했다([바이라인네트워크 우아콘 2025](https://byline.network/2025/10/1030/)).

## 영역별 권고: 백엔드는 Boot 4.1과 Modulith 2.1, 프론트는 Next 16.4, 지도는 MapLibre

### 백엔드와 데이터

여행노트는 그린필드이므로 3.x 마이그레이션 비용 없이 바로 **Spring Boot 4.1.x**로 시작해야 한다. Boot 4.0은 2025-11-20 GA로 Spring Framework 7, Jakarta EE 11, Jackson 3, JSpecify 널 안전성을 가져왔고([InfoQ Spring Boot 4](https://www.infoq.com/news/2025/11/spring-7-spring-boot-4)), 4.1.0은 2026-06-10 GA로 OSS 지원이 2027-06까지 이어지는 반면([spring.io Boot 4.1](https://spring.io/blog/2026/06/10/spring-boot-4/)) 3.5는 2026-06-30에 OSS 지원이 끝났고([endoflife.ai](https://endoflife.ai/article-spring-june-30-eol-wave)) 4.0.x는 2026-12-31에 끝난다([HeroDevs](https://www.herodevs.com/blog-posts/spring-boot-versions-eol-dates-and-latest-releases-april-2026)). 2026년 10월에 3.x나 4.0.x로 설계서를 쓰면 "버전 추적을 안 한다"는 신호가 된다. 런타임은 **Java 25 LTS**(2025-09-16 GA, [openjdk](https://openjdk.org/projects/jdk/25/))와 **Kotlin 2.3.x**(2.3.0은 2025-12-16, Java 25 지원, [JetBrains](https://blog.jetbrains.com/kotlin/2025/12/kotlin-2-3-0-released/))가 짝이다. Spring 측 Kotlin 리드 Sébastien Deleuze는 Boot 4.1이 Kotlin 2.3을 기준선으로 쓰며 JSpecify 덕분에 Spring API에서 unsafe platform type이 사라졌다고 설명한다([spring.io Next level Kotlin](https://spring.io/blog/2025/12/18/next-level-kotlin-support-in-spring-boot-4/)).

동시성 모델은 코루틴이 아니라 **가상 스레드**다. 가상 스레드는 Java 21에서 final이 됐고 `synchronized` 핀닝 문제는 JDK 24의 JEP 491에서 해소됐다([Microsoft Learn Java 25](https://learn.microsoft.com/en-us/java/openjdk/reasons-to-move-to-java-25)). Spring MVC + JPA 블로킹 스택에서는 `spring.threads.virtual.enabled=true` 한 줄로 끝나고, 코루틴을 도입하면 WebFlux와 R2DBC까지 끌려가 사이드 프로젝트 규모를 넘어선다. 가상 스레드를 켜면 병목이 스레드 고갈에서 HikariCP 풀 고갈로 옮겨간다는 전환 사례가 있으므로([besthub](https://www.besthub.dev/articles/virtual-threads-eliminated-thread-pools-until-mysql-connections-ran-out-0a7185b57756)), Hikari 풀 크기를 명시하고 Open-Meteo 같은 외부 호출에는 Framework 7 코어의 `@ConcurrencyLimit`과 `@Retryable`을 붙이는 것이 "가상 스레드를 이해하고 썼다"를 보여주는 포인트다. 이 두 애너테이션은 Spring Retry 프로젝트에서 영감을 받아 코어에 들어왔고 "스레드 풀 한계가 없는 Virtual Threads 환경에서 특히 유용"하다고 공식 문서가 적는다([docs.spring.io Resilience](https://docs.spring.io/spring-framework/reference/7.0/core/resilience.html)). 외부 의존이 Open-Meteo 하나뿐이라면 Resilience4j는 보류하고, 서킷브레이커 상태 전이를 꼭 보여주고 싶을 때만 2.4.0(Boot 4 지원)을 넣는다([resilience4j releases](https://github.com/resilience4j/resilience4j/releases)).

모듈 구조는 **Spring Modulith 2.1**(2026-06-11 GA)이 정답이다. 2.1은 Boot 슬라이스 테스트와 함께 동작하는 모듈 테스트, 이벤트 외부화 아웃박스, JDBC 이벤트 퍼블리케이션 스키마 자동 생성을 가져왔다([spring.io Modulith 2.1](https://spring.io/blog/2026/06/11/spring-modulith-2-1-ga-2-0-7-and-1-4-12-released/)). 이 레지스트리는 "트랜잭션 안에 이벤트 기록 → 커밋 후 비동기 처리 → 실패 시 재전송"이라는 아웃박스 패턴의 본질을 그대로 구현하므로([Confluent 아웃박스 강의](https://developer.confluent.io/courses/microservices/the-transactional-outbox-pattern/)), 면접관이 "왜 Kafka를 안 썼나"를 물으면 Kafka 없이 아웃박스를 구현했다고 답할 수 있다. `ApplicationModules.verify()` 테스트로 trip, share, user, weather 모듈 간 의존을 빌드에서 잡으면 배민의 "규칙은 코드 레벨에서"와 쿠팡의 "명확한 경계"에 동시에 대응한다. Modulith는 내부적으로 ArchUnit을 쓰므로 별도 ArchUnit 규칙은 배민이 경고한 대로 3~5개로 제한한다.

영속성에서 가장 중요한 결정은 **QueryDSL을 버리는 것**이다. 원본 QueryDSL은 2021년 7월 이후 릴리스가 없고([spring-data-jpa#3335](https://github.com/spring-projects/spring-data-jpa/issues/3335)), Spring Data 공식 문서는 "유지보수가 느려져 커뮤니티가 OpenFeign 아래로 포크했고 Spring Data는 포크를 best-effort로 지원"한다고 명시하며([docs.spring.io core-extensions](https://docs.spring.io/spring-data/jpa/reference/repositories/core-extensions.html)), 그 포크의 메인테이너는 Feign까지 전담하는 1인이다([sponsors.ecosyste.ms](https://sponsors.ecosyste.ms/accounts/velo)). 한국 면접에서 QueryDSL을 자주 묻기 때문에 "왜 안 썼는지"를 이 문구로 답할 준비를 하면 오히려 가점이다. 대안은 **Spring Data JPA(Hibernate 7.x)로 쓰기 모델, jOOQ 3.21로 읽기 모델**이다. jOOQ 3.21.0은 2026-03-24, 3.21.9는 2026-09-24에 나왔고 Jackson 3를 지원하며 PostgreSQL은 OSS 에디션 범위라 비용이 없다([jooq.org/notes](https://jooq.org/notes)). Hibernate 7은 detached 엔티티를 영속성 컨텍스트에 다시 붙이는 것을 금지하고 `save/update/saveOrUpdate`를 제거했으므로([Hibernate 7.0 마이그레이션 가이드](https://docs.hibernate.org/orm/7.0/migration-guide/migration-guide.html)), 컨트롤러에는 엔티티가 아닌 DTO와 커맨드만 노출하는 원칙이 자연스럽게 강제된다. Jackson 3는 패키지가 `tools.jackson`으로 바뀌고 `@JsonComponent`가 `@JacksonComponent`가 되며 날짜를 ISO-8601 문자열로 기본 직렬화하므로, 처음부터 새 이름을 쓰고 Next.js 타입과 날짜 포맷을 맞춘다([Boot 4.0 마이그레이션 가이드](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)). 마이그레이션은 Flyway를 유지하되 Boot 4에서는 `spring-boot-starter-flyway`를 명시해야 하고, Flyway 12.0.0은 2026-01-28에 나왔다([componentsource Flyway 12](https://www.componentsource.com/product/flyway/releases/2945096)).

데이터베이스는 **PostgreSQL 18**(2025-09-25 GA, 최신 마이너 18.6)이다. 18은 `uuidv7()` 내장 함수, 가상 생성 컬럼 기본값, 비동기 I/O로 스토리지 읽기 최대 3배, 다중 컬럼 B-tree 스킵 스캔, `md5` 인증 deprecated를 가져왔다([PostgreSQL 18 Released](https://www.postgresql.org/about/news/postgresql-18-released-3142/)). 19는 2026-09-24 Beta 4까지 나왔고 GA 공지는 아직 없다([postgresql.org](https://www.postgresql.org/)). 여행노트 PK는 `uuidv7()`로 B-tree 지역성을 얻되, 생성 시각이 노출되므로 공유 링크 슬러그는 별도 랜덤 토큰으로 둔다. 좌표는 **PostGIS 3.6.x**(3.6.0은 2025-09, PostgreSQL 18 지원, [PostGIS 3.6.0](https://www.postgis.net/2025/09/PostGIS-3.6.0/))의 `geography(Point,4326)` 생성 컬럼 + GiST 인덱스로 두고, 동선은 `geography(LineString)`으로 저장한다. 가이드 블록처럼 구조가 자주 바뀌는 콘텐츠만 jsonb에 넣고, 블록 타입이나 순서나 공개 여부처럼 필터링하는 필드는 일반 컬럼으로 승격한다. jsonb 인덱스는 `jsonb_path_ops` GIN이 `?` 연산자를 못 타고 순차 스캔으로 떨어진다는 함정이 있고([StackHarbor jsonb indexing](https://stackharbor.com/en/knowledge-base/pg-jsonb-indexing-gin-jsonpath/)), 한두 개 스칼라 키로만 필터한다면 B-tree 표현식 인덱스가 더 작고 정렬까지 지원한다([SitePoint JSONB performance](https://www.sitepoint.com/postgresql-jsonb-query-performance-indexing/)). pgvector는 0.8.1이 PostgreSQL 18을 지원하지만([SUSE PackageHub pgvector 0.8.1](https://packagehub.suse.com/packages/postgresql18-pgvector/0_8_1-160000_1_1)) 지금 테이블에 넣지 말고 설계 노트만 남긴다.

캐시와 세션은 현재 설계의 Redis를 유지하되 **Valkey 9.1 또는 Redis 8** 중 라이선스를 설명할 수 있는 쪽을 고른다. Redis 8.0은 2025-05-01에 AGPLv3를 세 번째 라이선스로 추가했고([InfoQ Redis AGPL](https://www.infoq.com/news/2025/05/redis-agpl-license)), Valkey는 BSD-3로 9.0(2025-10-21)과 9.1(2026-05-19, 문자열 키당 메모리 최대 44% 절감)을 냈다([Valkey Blog](https://valkey.io/blog/)). 둘 다 RESP 호환이라 Spring Data Redis + Lettuce로 붙고, Valkey용 공식 Spring Data Valkey도 GA다([valkey.io Spring Data Valkey](https://valkey.io/blog/spring-data-valkey/)). Redis를 유지하는 결정적 이유는 뒤에 나오는 BFF 세션 저장소다. 다만 "API 인스턴스 1대면 Caffeine으로 충분하고 수평 확장 시 Valkey로 교체"라는 경로를 ADR로 남기면 과잉 설계 질문을 미리 막는다. Postgres UNLOGGED 테이블은 일반 테이블 대비 처리량 향상이 약 12~13%에 그친다는 벤치마크가 있어([freeCodeCamp Postgres as cache](https://www.freecodecamp.org/news/how-to-use-postgresql-as-a-cache-queue-and-search-engine/)) 날씨 캐시 대안으로는 언급만 한다.

인증은 **BFF 패턴에 불투명 세션 ID 쿠키 + Spring Session Redis**다. 토큰이 백엔드를 떠나지 않으면 BFF의 세션 삭제로 즉시 접근을 폐기할 수 있고 브라우저로 보낸 JWT로는 불가능하다는 것이 Baeldung의 정리이며([Baeldung BFF](https://www.baeldung.com/spring-cloud-gateway-bff-oauth2)), Auth0도 세션 쿠키는 Secure + HttpOnly 필수, 토큰은 서버 측 저장을 권한다([Auth0 BFF](https://auth0.com/blog/the-backend-for-frontend-pattern-bff/)). Spring Security 7.0은 SPA용 `http.csrf((csrf) -> csrf.spa())` DSL을 추가하고 OAuth2 비밀번호 그랜트를 제거했으며 OAuth2 스타터 이름이 `spring-boot-starter-security-oauth2-client`로 바뀌었다([docs.spring.io Security 7.0 What's New](https://docs.spring.io/spring-security/reference/7.0/whats-new.html)). 카카오는 내장 provider가 아니라서 수동 등록이 필요하고, 401 "[no body]" 오류는 `client-authentication-method: client_secret_post`로 해결되며 redirect URI의 127.0.0.1과 localhost 불일치가 가장 흔한 함정이다([velog 카카오 OAuth2 오류](https://velog.io/@zosungwoo/Spring-Boot-카카오-OAuth2-로그인-오류-1.-authorizationrequestnotfound-2.-invalidtokenresponse)). Spring Session Redis는 기본 Java 직렬화를 쓰므로 JSON 직렬화 빈으로 교체하고, 만료 세션 정리가 Keyspace Events에 의존한다는 점을 설정에 반영한다([docs.spring.io Spring Session Redis](https://docs.spring.io/spring-session/reference/4.0/configuration/redis.html)). Vercel과 API 서버가 다른 origin이면 SameSite=Lax 쿠키가 API 호출에 붙지 않으므로 Next.js rewrites로 `/api/*`를 same-origin으로 만든다.

API 계약은 **springdoc-openapi 3.1.x**(Boot 4.1 대응, [newreleases springdoc 3.1.0](https://newreleases.io/project/github/springdoc/springdoc-openapi/release/v3.1.0))로 스펙을 내고 CI에서 JSON을 커밋해 PR diff로 API 변경을 리뷰하는 것이 가장 가벼운 계약 테스트다. 구 `openapi-typescript-codegen`은 유지보수가 끝났고 README가 `@hey-api/openapi-ts`로 이전을 요청한다([yarnpkg openapi-typescript-codegen](https://classic.yarnpkg.com/en/package/openapi-typescript-codegen)). 관측성은 Boot 4.0의 **`spring-boot-starter-opentelemetry`**(OTLP 메트릭과 트레이스, OpenTelemetry SDK 1.54.0, [Boot 4.0 Release Notes](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Release-Notes))에 3.4부터의 구조화 로깅 `logging.structured.format.console=ecs`([spring.io 구조화 로깅](https://spring.io/blog/2024/08/23/structured-logging-in-spring-boot-3-4))를 더한다. 네이버 검색 모니터링 플랫폼이 OpenTelemetry Collector 기반으로 전환했고([D2 OpenTelemetry](https://d2.naver.com/helloworld/1104856)) 여기어때가 Pinpoint에서 OpenTelemetry + Grafana(Mimir, Tempo, Loki)로 옮기고 있다는 점에서([여기어때 옵저버빌리티](https://techblog.gccompany.co.kr/%EC%83%88%EB%A1%9C%EC%9A%B4-%ED%8C%80%EC%97%90-%EA%B8%B0%EC%97%AC%ED%95%98%EA%B8%B0-%EA%B7%B8%EB%A6%AC%EA%B3%A0-%EA%B8%B0%EC%97%AC%EC%9D%98-%ED%99%95%EC%9E%A5-feat-%EC%A0%84%EC%8B%9C%EA%B0%9C%EB%B0%9C%ED%8C%80-%EC%98%B5%EC%A0%80%EB%B2%84%EB%B9%8C%EB%A6%AC%ED%8B%B0-%ED%96%A5%EC%83%81-%EC%8B%9C%ED%82%A4%EA%B8%B0-c39614694661)) OTel + Grafana는 국내 대기업과 어휘가 겹치는 스택이다.

테스트 스택은 **JUnit 6.1 + MockK 1.14 + Testcontainers 2.0 + Modulith 모듈 테스트**다. JUnit 6.0.0은 2025-09-30 GA로 Java 17과 Kotlin 2.2를 최소로 하고 Kotlin `suspend` 테스트를 지원하며([docs.junit.org 6.0.0](https://docs.junit.org/6.0.0/release-notes/)), Boot 4는 `@MockBean` 대신 `@MockitoBean`, `@SpringBootTest`에 `@AutoConfigureMockMvc` 명시, 새 `RestTestClient`를 요구한다([Boot 4.0 마이그레이션 가이드](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)). Testcontainers 2.0은 모듈명에 `testcontainers-` 접두어가 붙고 1.x 좌표가 해석되지 않으므로 튜토리얼 복사는 위험하다([issoh Testcontainers 2.0 정리](https://www.issoh.co.jp/tech/details/4629/)). Kotest는 런너까지 쓰면 Spring 슬라이스 테스트와 마찰이 생기므로 어서션만 선택적으로 쓴다. 빌드는 **Gradle 9.x Kotlin DSL**(9.0.0은 2025-07-31, Configuration Cache 선호, [Gradle 9.0 릴리스 노트](https://docs.gradle.org/9.0.0/release-notes.html))이고, 시작 시간은 GraalVM native 대신 **JDK AOT cache**(JEP 483, Spring PetClinic 최대 40% 빠른 시작, 코드 변경 불필요, [InfoQ Leyden](https://www.infoq.com/news/2025/03/java-24-leyden-ships))를 Dockerfile 멀티스테이지의 학습 실행 단계로 넣는다. ### 프론트엔드

**Next.js 16.4**(2026-10-06)는 "Starting with Next.js 16.4, we're excited to recommend Cache Components as the best choice for every Next.js app"이라고 선언했고 `create-next-app`의 새 앱은 Cache Components가 기본이며 Next.js 17에서 기본값이 된다([Next.js 16.4](https://nextjs.org/blog/next-16-4)). Next.js 16(2025-10-21)은 Turbopack 기본화, React Compiler 지원 안정화, `experimental.ppr` 플래그 제거와 `'use cache'` 기반 Cache Components 통합, `middleware.ts`를 Node 런타임의 `proxy.ts`로 교체, `next lint` 제거를 가져왔다([Next.js 16](https://nextjs.org/blog/next-16)). 16.3(2026-08-03)은 `cacheComponents: true` + `partialPrefetching: true`의 Instant Navigations, `@next/playwright`의 `instant()` 테스트 헬퍼, 실험적 `useOffline()` 훅, TypeScript 7 타입체크를 추가했다([Next.js 16.3](https://nextjs.org/blog/next-16-3)). 여행노트처럼 "공개 콘텐츠(공유 링크)와 로그인 사용자 에디터가 섞인 앱"은 Cache Components가 정확히 겨냥한 사례다. 공유 페이지에는 `'use cache'` + `cacheLife`, 단발성 쓰기에는 Server Action + `updateTag()`, 드래그 재정렬처럼 초당 여러 번 일어나는 상호작용은 TanStack Query mutation + 디바운스로 처리하는 하이브리드가 공식 API 설계와 맞는다. State of React 2025에서 Server Components와 Server Functions가 "polarizing"하고 각각 3·4번째로 싫어하는 기능이었다는 점은([certificates.dev State of React 2025](https://certificates.dev/blog/breaking-down-state-of-react-2025-results)) 클라이언트 상호작용을 `'use client'` 경계로 명확히 분리하라는 신호다. 2025-12-03의 CVE-2025-66478(React Server Components 프로토콜의 인증 없는 원격 코드 실행)은([React Blog](https://react.dev/blog)) 패치 추적을 운영 절차에 넣어야 하는 이유이고, 16.4의 `next upgrade --agent`가 그 자동화 경로다.

React는 **19.3**(2026-09-09)에서 View Transitions와 Fragment Refs가 안정화됐고([React 19.3](https://react.dev/blog/2026/09/09/react-19-3)), React Compiler 1.0은 2025-10-07에 안정 릴리스되어 lint 규칙이 `eslint-plugin-react-hooks` recommended에 포함됐다([React Compiler v1.0](https://react.dev/blog/2025/10/07/react-compiler-1)). Compiler는 Next 16에서 기본 off이고 Babel 경로라 빌드가 느려지지만, 드래그와 지도처럼 리렌더에 민감한 UI의 수동 memo를 줄이는 효과가 커서 켜는 것이 맞다. 16.3의 Rust 컴파일러(`turbopackRustReactCompiler`)는 아직 experimental이다.

E2E는 `getByRole` 같은 접근성 셀렉터와 `@axe-core/playwright`를 쓰면 토스 TMC 25의 "누구나 작성하는 E2E 테스트를 향하여: 접근성에서 찾은 답" 세션과 같은 신호를 낸다([토스 TMC 25 세션](https://toss.im/tmc-25/sessions/engineering/server-21)). 네이버 D2의 "AI 에이전트를 위한 Playwright E2E 테스트 하네스" 글은 에이전트가 직접 테스트를 작성하고 검증하는 워크플로를 다루므로([D2 Playwright 하네스](https://d2.naver.com/helloworld/6811215)), Playwright E2E가 AI 산출물 통제 장치로 읽히는 효과도 있다. 린트는 Next 16이 "Biome 또는 ESLint"를 공식 선택지로 명시했으므로 **Biome 2.5**(500개 이상 규칙, 2026-06-05, [Biome Blog](https://biomejs.dev/blog/))로 포맷과 일반 규칙을, ESLint 10으로 `eslint-plugin-react-hooks`의 React Compiler 규칙과 `@next/eslint-plugin-next`를 돌리는 병행 구성이 현실적이다. **TypeScript 7.0**(2026-07-08, Go 네이티브, 전체 빌드 8~12배)은 `tsc`와 Next 빌드에 바로 쓸 수 있지만 7.0에 프로그램 API가 없어 typescript-eslint는 `@typescript/typescript6` alias로 6.0을 병행해야 한다([Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). 성능 측정은 Lighthouse CI가 2025-06-25 이후 릴리스가 없어 모멘텀이 약하므로, PR 단계의 상한선 가드 1회 + Vercel Speed Insights(INP 목표 200ms 이하, [Speed Insights Metrics](https://vercel.com/docs/speed-insights/metrics))로 역할을 나눈다. 2025 Web Almanac 기준 모바일 사이트 23%가 "good" INP에 미달한다는 Vercel 가이드는([Vercel KB Core Web Vitals](https://vercel.com/kb/guide/how-to-improve-core-web-vitals)) 랩 점수가 올그린이어도 필드 데이터는 다를 수 있다는 근거다.

PWA는 세 층으로 나뉜다. Next.js PWA 가이드는 `app/manifest.ts`와 VAPID + `web-push` + Server Actions 웹 푸시까지 다루지만 서비스 워커 캐싱은 Serwist를 지목하고, iOS Safari는 `beforeinstallprompt`를 지원하지 않아 커스텀 설치 버튼을 비권장한다([Next.js PWA guide](https://nextjs.org/docs/app/guides/progressive-web-apps)). `next-pwa`는 2022-08-23 이후 게시가 없어 사실상 폐기됐고 **Serwist 9.5.13**(2026-10-04)이 현역이다([Serwist docs](https://serwist.pages.dev/docs/next/getting-started)). 앱 셸은 Serwist precache, 일정 데이터는 TanStack Query persist, 지도 타일은 OpenFreeMap 정책(1회 3,000타일 또는 50MB) 안에서 일본 도시 영역만 사전 캐시한다. 국제화는 **next-intl 4.14**(주간 약 700만)가 Next.js 16.3의 `next/root-params`를 공식 지원하므로([next-intl blog](https://next-intl.dev/blog)) 한국어 단일 언어로 출발해도 `[lang]` 루트 세그먼트를 처음부터 잡아둔다. OG 이미지는 `next/og` `ImageResponse`가 JSX, CSS, 폰트, 이미지를 포함해 **번들 500KB 제한**이 있고 ttf/otf를 권장하므로([Next.js ImageResponse](https://nextjs.org/docs/app/api-reference/functions/image-response)) 한글 폰트는 필요한 글리프만 추출한 서브셋 ttf를 모듈 스코프에서 1회 읽는다. 모노레포는 `apps/web`과 `packages/ui` 두 패키지라면 pnpm workspaces로 충분하고, Turborepo 2.11은 CI 캐시나 Storybook/Vitest 병렬 실행이 느려질 때 얹는다. Next.js 16.3의 빌드 디스크 캐시가 CI를 최대 5.5배 빠르게 하고([Next.js 16.3](https://nextjs.org/blog/next-16-3)) 16.4가 pnpm global virtual store를 직접 지원하기 시작했으므로([Next.js 16.4](https://nextjs.org/blog/next-16-4)) Turborepo 없이도 기본은 된다.

### 플랫폼, 운영, 보안

호스팅 비용 밴드는 1인 프로덕션 기준 **월 $55~75**다. Vercel Pro는 $20/월 플랫폼 요금에 $20 월 사용 크레딧이 포함되고([Vercel Pro plan](https://vercel.com/docs/plans/pro)), Hobby는 "모든 상업적 사용은 Pro 또는 Enterprise 필요"라 포트폴리오로 공개 운영할 때는 Pro가 깔끔하다([Vercel Fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines)). JVM API는 Vercel 컨테이너 함수에 올릴 수 있지만 5분 무트래픽 시 축소되어([Vercel Docker deployments](https://vercel.com/kb/guide/does-vercel-support-docker-deployments)) JVM 콜드 스타트 문제가 생기므로 **서울 또는 도쿄 리전의 상시 가동 컨테이너 1대**가 맞다. Fly.io는 도쿄(nrt) shared-cpu-1x 1GB가 월 $8.76이고 신규 조직 무료 티어는 없다([Fly.io Pricing](https://docs.fly.io/about/pricing)). Cloud Run은 서울(asia-northeast3)이 Tier 2 요금이라 도쿄보다 비싸고([Cloud Run locations](https://docs.cloud.google.com/run/docs/locations)) `min-instances=1`이 필요해 무료 티어 의미가 줄어든다. **AWS App Runner는 2026-04-30 이후 신규 고객을 받지 않으므로**([AWS App Runner availability change](https://docs.aws.amazon.com/ja_jp/apprunner/latest/dg/apprunner-availability-change.html)) 2026년 설계서에 넣으면 최신 동향을 모른다는 신호가 된다. 성숙도는 플랫폼 이름이 아니라 SHA 태그 이미지, `/actuator/health/readiness` 기반 전환, 롤백 절차 문서, GitHub Actions 한 번으로 끝나는 배포에서 나온다. 단일 VM이라도 Docker Compose로 blue/green 컨테이너 두 개와 Caddy를 두고 스크립트로 전환하면 K8s 없이 설명 가능하며, Boot 4.0은 liveness/readiness 프로브가 기본 활성이다([Boot 4.0 마이그레이션 가이드](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)).

관리형 Postgres는 **Supabase 서울 리전 Pro $25/월**이 프로덕션 1순위다. Supabase는 Northeast Asia (Seoul) `ap-northeast-2`를 제공하고([Supabase Regions](https://supabase.com/docs/guides/platform/regions)), Pro는 8GB 디스크, 100,000 MAU, 브랜칭 $0.01344/브랜치-시간, 지출 상한 기본 활성이다([Supabase Pricing](https://supabase.com/pricing)). Neon은 아시아 리전이 싱가포르뿐이라([Neon Regions](https://neon.com/docs/introduction/regions)) 한국에서 RTT 약 200ms가 보고됐고([Neon Community](https://community.neon.tech/t/eta-on-northeast-asia-regions/541)), 2025년 5월 Databricks에 약 $1B에 인수됐다([TechTarget](https://www.techtarget.com/searchdatamanagement/news/366623864/Databricks-adds-Postgres-database-with-1B-Neon-acquisition)). Neon Free(프로젝트당 100 CU-시간, 브랜치 10개, [Neon Pricing](https://neon.com/pricing))는 PR별 프리뷰 브랜치 DB로만 쓰는 하이브리드가 가능하지만 벤더가 둘이 되는 비용을 감안한다. Supabase를 Postgres 호스팅으로만 쓰고 Auth와 Storage를 안 쓰는 이유는 ADR에 적어야 "왜 BaaS를 골랐나"에 답할 수 있다.

CI/CD와 공급망 보안은 비용 0원으로 갖출 수 있다. GitHub Actions는 2026-01-01부터 호스티드 러너 가격을 최대 39% 인하했고 공개 저장소는 계속 무료이며 셀프호스티드 러너 과금은 연기됐다([GitHub 2026 pricing](https://github.com/resources/insights/2026-pricing-changes-for-github-actions)). OIDC로 잡마다 단기 토큰을 받으면 클라우드 키를 GitHub Secrets에 넣을 필요가 없고 `sub`에 `environment:production` 조건을 걸 수 있다([GitHub Docs OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect)). 액션은 `tj-actions/changed-files` 침해가 계기가 된 태그 재지정 공격을 막기 위해 전체 SHA로 고정하고 Renovate의 `helpers:pinGitHubActionDigests` 프리셋으로 자동 갱신한다([Renovate GitHub Actions manager](https://docs.renovatebot.com/modules/manager/github-actions)). Artifact Attestations는 Sigstore 기반으로 공개 저장소는 public-good 투명성 로그에 기록되며([GitHub Docs Artifact attestations](https://docs.github.com/ru/actions/concepts/security/artifact-attestations)), Trivy로 CycloneDX SBOM을 만들어 첨부한다. IaC는 **OpenTofu 1.11**(MPL 2.0, 2025-04 CNCF 가입, 상태 암호화, ephemeral 리소스, [Linuxiac OpenTofu 1.11](https://linuxiac.com/opentofu-1-11-introduces-ephemerality-for-safer-temporary-credentials/))을 DNS, R2 버킷, 컨테이너 서비스 1개 범위로만 적용한다. Terraform 1.6+는 BSL 1.1이라 2026년에는 질문거리가 된다([jorijn OpenTofu vs Terraform](https://jorijn.com/en/blog/opentofu-vs-terraform-2026-the-fork-finally-diverged/)).

관측성은 **Grafana Cloud Free + Sentry Developer**로 0원이다. Grafana Cloud Free는 메트릭 10k 활성 시리즈, 로그·트레이스·프로파일 각 50GB(14일), k6 500 VUh, Frontend Observability 5만 세션을 영구 무료로 제공하고([Grafana Cloud Pricing](https://grafana.com/pricing/)), Sentry Developer는 에러 5k, 트레이싱 5M span, 세션 리플레이 50건이다([Sentry Pricing](https://sentry.io/pricing/)). Spring Boot 4 스타터에서 OTLP를 Grafana Cloud 엔드포인트로 직결하면 호스트가 1대일 때 Collector가 필요 없고, "Collector를 안 둔 이유"를 ADR로 적는 편이 성숙한 판단으로 읽힌다. Datadog은 무료 5호스트가 있지만 APM $31/호스트/월과 로그 $0.10/GB로 번지기 쉽고 실제 청구가 초기 추정의 2~3배가 되는 경우가 흔해([DoiT Datadog pricing](https://www.doit.com/blog/datadog-pricing-explained)) 1인 프로젝트에서 고르면 비용 감각을 의심받는다. 토스페이먼츠가 "장애 대응의 시작은 감지"라는 전제로 Prometheus, Mimir, Grafana로 메트릭과 알람을 구성했다는 글은([toss.tech 하이브리드 클라우드](https://toss.tech/article/payments-legacy-9)) Grafana 계열이 면접 친화적인 어휘임을 뒷받침한다. SLO는 공유 페이지 가용성 99.5%/30일, API p95 400ms 이내, OG 이미지 생성 성공률 99% 같은 세 개를 README에 적고 에러 버짓 소진 시 "기능 배포 중단" 규칙을 명시한다. 부하 테스트는 **k6 2.1.0**(2026-06-30, AGPL-3, [Wikipedia k6](https://en.wikipedia.org/wiki/K6_(software)))으로 "일상 10 RPS 이하, 공유 링크 바이럴 시 100 RPS 5분 버스트, 공유 페이지 캐시 적중률 90% 이상"이라는 세 숫자를 재현하고 HikariCP 풀과 JVM 콜드 스타트가 어디서 걸리는지 그래프로 남긴다.

이미지는 Vercel이 2025-02-18부터 과금을 소스 이미지 수에서 "변환 횟수 + 캐시 읽기/쓰기"로 바꿔 Hobby 5K 변환/월 이후 $0.05~0.0812/1K이고 캐시 MISS마다 과금된다([Vercel Image Optimization pricing](https://vercel.com/docs/concepts/image-optimization/limits-and-pricing)). 사용자 업로드 이미지가 쌓이는 서비스는 브라우저에서 **Cloudflare R2**(무료 10GB, egress 무료, [Cloudflare pricing](https://developers.cloudflare.com/workers/platform/pricing/))에 presigned URL로 직접 올리고 Cloudflare Images(월 5,000 고유 변환 무료, 이후 $0.50/1K, [Cloudflare Images pricing](https://developers.cloudflare.com/images/pricing/))로 변환하면 Vercel 변환 과금과 egress를 모두 피한다.

개인정보는 2025년 개인정보위 자료 두 건을 설계에 반영한다. 개인정보위는 2025-02-13 네이버, 카카오, 구글, 메타, 애플 소셜 로그인 점검 결과를 발표하며 5개 사업자 모두 토큰 폐기 기능을 제공하지만 거의 사용되지 않고 폐기되지 않은 토큰은 해킹 위험이 있다고 지적했다([보안뉴스 소셜 로그인 점검](http://www.boannews.com/news/articleView.html?idxno=135941)). 따라서 회원 탈퇴 API는 DB 레코드 삭제 또는 익명화, 소셜 제공자 토큰 revoke 호출, R2 이미지 삭제 큐잉의 세 단계로 구현하고 README에 적는다. 2025-04-21 공개된 개인정보 처리방침 작성지침 개정본은 법령 필수사항과 권장사항을 구분하고 계약 이행 목적은 동의 없이 처리 가능하다고 정리했으므로([대륜 뉴스레터](https://www.daeryunlaw.com/newsletter/news/151)) 처리방침에 수집 항목, 보유기간, 위탁과 국외 이전 벤더(Vercel, Supabase, Sentry, Grafana Cloud)를 명시한다. 레이트리밋은 Cloudflare Free의 규칙 1개(IP 기준, 10초 창, [Cloudflare Rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/))를 로그인과 공유 링크 생성 경로에 걸고, 사용자별 세밀한 제한은 bucket4j로 처리한다. 기능 플래그는 Unleash 서버를 띄우지 않고 OpenFeature SDK + DB 테이블 프로바이더로 점검 모드 하나부터 운영하며, 배민이 기능 플래그로 노출 비율과 런타임 롤백을 구현한 글의 "배포와 릴리스의 분리" 어휘를 쓴다([배민 실험플랫폼](https://techblog.woowahan.com/9935/)).

### AI, 실시간 협업, 한국 플랫폼 연동

LLM 기능은 **조건부 채택**이다. 토스 AI 플랫폼 글이 "모델을 호출할 권한과 사내 도구를 실행할 권한은 별개"라며 예산과 TPM 한도, 입력 가드레일, Langfuse 트레이스, PII 마스킹을 갖춘 뒤 배포했다는 점([toss.tech AI 플랫폼](https://toss.tech/article/ai-platform-foundation))과 Toss Benchmark의 "범용 시험을 잘 푸는 것과 토스 도메인 업무를 처리하는 것은 다른 능력"이라는 결론([toss.tech Toss Benchmark](https://toss.tech/article/toss-benchmark))을 합치면, 면접관이 인정할 AI는 자유 생성 챗봇이 아니라 **비정형 입력(블로그 글, 예약 메일)을 스키마로 정규화하고 시간과 동선 타당성을 결정론적 계산으로 검증하는 기능**이다. Claude의 구조화 출력은 `output_config.format`으로 JSON Schema 제약 디코딩을 제공하며 베타 헤더가 필요 없고 `strict: true` 툴과 병행할 수 있지만 재귀 스키마, `minimum/maximum`, `minLength/maxLength`는 쓸 수 없고 `additionalProperties`는 `false`만 허용한다([Claude Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). 좌표 범위 검증은 서버에서 한다. 비용은 Haiku 5.5가 $0.10/$0.50, Sonnet 5.5가 $2/$10(입력/출력 $/MTok)이고 프롬프트 캐시 읽기는 Sonnet 5.5가 0.05x, 배치 API는 50% 할인이라([Claude Pricing](https://platform.claude.com/docs/en/about-claude/pricing)) 블로그 글 1편에서 stops를 추출하는 데 Sonnet 5.5로 약 $0.02, Haiku 5.5로 약 $0.001이 든다. 월 수천 건 규모에서는 모델 선택보다 캐시 가능한 시스템 프롬프트를 앞에 고정하는 것이 비용을 좌우한다. 구현 위치는 데이터와 검증 로직이 있는 Spring 쪽이 "AI 결과를 도메인 규칙으로 검증한다"는 서사를 만들기 쉽고, Boot 4.1이면 **Spring AI 2.0**(2026-06-12 GA, Boot 4 필수, provider-native 구조화 출력, `StructuredOutputValidationAdvisor`, [Spring AI 2.0.0 GA](https://spring.io/blog/2026/06/12/spring-ai-2-0-0-GA-available-now/))을 쓸 수 있지만 Anthropic Java SDK 직접 호출이 표면적이 더 작다. 평가는 Promptfoo(MIT, CI 게이트) + 골든셋 20~50건, 트레이싱은 Langfuse Hobby(월 5만 유닛 무료, [Langfuse pricing](https://langfuse.com/pricing))로 1인 규모에 충분하다. 앱을 MCP 서버로 노출하는 것은 2026-07-28 개정으로 세션과 `initialize` 핸드셰이크가 제거되어 stateless HTTP가 표준이 됐지만([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) Spring AI 2.0이 번들한 MCP Java SDK 2.0.0은 2025-11-25 스펙이라 한 단계 뒤다. 기술 시연 가치는 있으나 사용자 가치는 낮아 조건부다.

실시간 협업은 **CRDT 없이 "서버 권위 + 버전 기반 낙관적 잠금 + 필드 단위 LWW + fractional index + SSE presence"**로 시작한다. 여행노트의 충돌은 같은 stop의 같은 필드 동시 수정, 순서 재배열, 삭제 대 수정 세 가지인데, 필드 단위 LWW와 서버 버전 번호로 앞뒤 두 가지는 "마지막 저장이 이기되 상대에게 토스트로 알림"이 되고, 재배열은 정수 인덱스 대신 fractional index를 쓰면 대부분 자연 병합된다. 우아콘 2025의 "배달의민족 주문~!: ServerSentEvents로 실시간 알림 전송하기" 세션은 SSE가 배민이 실제로 쓰는 패턴임을 보여준다([배민 우아콘 2025 후기](https://techblog.woowahan.com/24289/)). Yjs 13.6.33 + Hocuspocus 4(2026-05-08 안정, Node 22+ 필수, [Hocuspocus 4 release](https://tiptap.dev/blog/release-notes/hocuspocus-4-stable-release))는 memo 필드를 여러 명이 동시에 타이핑하는 UX나 오프라인 편집 후 병합을 약속할 때만 정당화되며, 그때도 memo 텍스트만 Y.Text로 두는 하이브리드가 설명하기 쉽다. Hocuspocus는 별도 Node 프로세스이므로 Spring 단일 서버 구성에 운영 대상이 하나 늘어난다는 점을 리스크로 적어야 한다. Zero 1.0(2026-06)은 클라이언트 번들이 718KB(압축 232KB)이고 SSR을 지원하지 않으며([InfoQ Zero 1.0](https://infoq.com/news/2026/06/zero-version-1)), Electric, PowerSync, TanStack DB 0.6(아직 베타)은 Postgres 논리 복제와 별도 서비스를 요구하는 "쿼리 기반 부분 동기화" 인프라라 2~5명 동시 편집에는 운영 복잡도 대비 이득이 없다. Liveblocks는 2명 이상 접속 시 분당 $0.002로 소규모에는 사실상 무료지만 Free 플랜은 룸당 10 연결과 브랜딩 요구가 있고 데이터가 외부에 있다([Liveblocks pricing](https://liveblocks.io/pricing.md)).

한국 플랫폼 연동에서 설계서에 반드시 반영할 변경점이 넷 있다. 첫째, **카카오맵 API는 2026-07-21부터 "개발자 계정당 첫 번째 활성화 앱에만 무료 쿼터"**를 주고(지도 SDK 일 30만, 로컬 API 각 일 10만, 신규 경로와 정적지도 일 1,000건) 두 번째 앱부터는 비즈월렛 연결이 필요하다([Kakao DevTalk 정책 공지](https://devtalk.kakao.com/t/api-notice-on-new-kakao-map-api-features-and-free-quota-policy/150222), [Kakao 쿼터 문서](http://developers.kakao.com/docs/ko/getting-started/quota)). 국내 여행을 추가할 때 dev/prod 앱을 분리하면 두 번째 앱이 유료가 되므로 하나의 앱에 두 도메인을 등록한다. 둘째, **카카오톡 공유는 일 30,000건 무료**이고 초과분은 건당 50원이되 2026-02-02~12-31은 한시적으로 10원이라([Kakao 쿼터 문서](http://developers.kakao.com/docs/ko/getting-started/quota)) "공유 링크" 핵심 기능 비용이 0원이고, `sendDefault()` 피드 템플릿이면 템플릿 심사 없이 쓸 수 있다([Kakao 공유 JS](https://developers.kakao.com/docs/latest/ko/kakaotalk-share/js-link)). 셋째, **카카오 로그인에서 이메일을 필수 동의로 만들거나 이름과 전화번호를 받으려면 비즈 앱 전환과 비즈니스 정보 심사(영업일 3~5일)**가 필요하고([Kakao 로그인 사전 설정](http://developers.kakao.com/docs/ko/kakaologin/prerequisite)), 전환 후에도 승인 전까지 해당 항목은 `null`이다([DevTalk 150606](https://devtalk.kakao.com/t/topic/150606)). 이메일과 닉네임과 프로필 이미지만 받는 최소 수집이 심사 없이 가장 빠르다. 구글은 FedCM 전환 외에 추가 심사가 없고 명시적 마감일도 없다([Google FedCM migration](https://developers.google.com/identity/gsi/web/guides/fedcm-migration)). 네이버 로그인은 전체 화면 캡처를 제출하는 최종 검수가 필수라 2차 우선순위, 애플은 App Store 심사 지침 4.8이 App Review 대상 앱에 적용되고 웹사이트 적용 여부는 명시가 없어([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)) 웹 전용 서비스에서는 보류한다. 넷째, **Open-Meteo 무료 티어는 비상업용 한정(일 10,000건)**이며 KMA와 JMA 모델을 모두 제공하고 데이터는 CC BY 4.0이다([Open-Meteo pricing](https://open-meteo.com/en/pricing)). 광고나 결제 없이 운영하면 무료 범위이고 수익화 시 유료 Standard로 올리거나 국내 구간만 기상청 공공데이터로 분리한다.

알림은 **VAPID 웹 푸시를 직접 구현**한다. Apple은 iOS 16.4 이상의 홈 화면 웹앱과 macOS 13 Safari 16 이상에서 웹 푸시를 지원하고 Apple Developer Program 가입이 필요 없으며 RFC 8030 표준 VAPID를 그대로 쓰되, 보이지 않는 푸시는 지원하지 않아 수신 즉시 표시하지 않으면 권한을 회수한다([Apple Sending web push notifications](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)). iOS 18.4부터는 서비스워커 없이 JSON만으로 알림을 표시하는 Declarative Web Push가 추가됐다([WebKit Declarative Web Push](https://webkit.org/?p=16535)). FCM 웹 SDK는 같은 VAPID 키를 쓰는 래퍼이고 문서에 Safari 언급이 없어([Firebase Cloud Messaging JS](https://firebase.google.com/docs/cloud-messaging/js/client)) Firebase 의존을 추가할 이유가 없다. 카카오 알림톡은 건당 약 8~10원(2차, [Hackle message price](https://docs.hackle.io/crm-marketing/message-price))이지만 카카오톡 채널 개설, 템플릿 사전 심사, 딜러사 계약, 전화번호 수집(비즈 앱 심사)이 1인 B2C에 과하다. "iOS는 홈 화면에 추가해야 알림이 온다"는 안내 UX 자체가 PWA 완성도를 보여주는 포트폴리오 요소다.

## 과잉 설계로 읽힐 위험과 그 경계

"공고에 있는 키워드"와 "1인 프로젝트에서 정당화되는 기술"이 갈라지는 지점이 이 보고서의 핵심 긴장이다. 공고가 Kafka, Kubernetes, MSA, gRPC를 반복한다고 해서 여행노트에 넣으면, 면접관은 정확히 그 지점에서 "RabbitMQ 대비 Kafka를 고른 이유"와 "서비스 간 트랜잭션과 데이터 일관성"을 묻는다([인프런 커뮤니티](https://www.inflearn.com/vi/community/questions/1742305/이것도-포트폴리오에-넣어야할까요)). 반대로 Kafka 없이 Modulith 이벤트 레지스트리로 아웃박스를 구현하고 "현재 단일 배포 단위라 브로커가 불필요하며 분리 지점은 share 모듈"이라고 ADR에 적으면, 배민이 Temporal 대신 Flowkit을 만든 "필요한 악기만 뽑아 가벼운 실내악으로 편곡"한 서사([배민 Flowkit](https://techblog.woowahan.com/26832/))와 같은 구조가 된다. 레드 플래그를 피하는 가장 효과적인 장치는 **ADR에 고려한 대안과 기각 이유를 적는 것**인데, 커뮤니티가 꼽는 탈락 질문이 전부 "대안 비교" 질문이기 때문이다.

같은 논리가 이 보고서의 권고 자체에도 적용된다. Spring Modulith, jOOQ, PostGIS, OpenTelemetry, Attestation, OpenTofu, Storybook, Vitest Browser Mode, k6를 전부 넣으면 1인 프로젝트치고 도구가 많다는 인상을 줄 수 있다. 배민 ArchUnit 글이 "규칙 세트가 커질수록 유지 비용 증가, 핵심 규칙부터"라고 경고한 것처럼([배민 ArchUnit](https://techblog.woowahan.com/26835/)), 각 도구는 "그것이 잡은 문제"가 있을 때만 성숙도 신호가 된다. 경계를 정하는 기준은 세 가지다. 첫째, **운영 대상이 늘어나는가**. Hocuspocus(Node 프로세스), OTel Collector, Unleash 서버, Kafka, Kubernetes는 호스트 1대 운영에 관리 대상을 추가하므로 보류한다. 둘째, **대체 가능한 코어 기능이 이미 있는가**. Resilience4j는 Framework 7 `@Retryable`로, Kafka는 Modulith 레지스트리로, Lighthouse CI는 Speed Insights로, FCM은 VAPID로 대체되므로 피한다. 셋째, **그 기술을 썼을 때 면접에서 설명할 "문제"가 실제로 있는가**. pgvector는 장소 임베딩 테이블이 없으면 설명할 문제가 없고, CRDT는 memo 동시 타이핑 요구가 없으면 없다.

| 항목 | 지금 과잉인 이유 | 정당화되는 조건 |
|---|---|---|
| Kafka / RabbitMQ | 단일 배포 단위, 토픽 1개는 "이력서용 키워드"로 읽힘 | 외부 소비자(알림 서비스, 분석 파이프라인)가 생기거나 모듈을 별도 배포로 분리할 때 |
| Kubernetes / MSA | 호스트 1대, 1인 운영; 공고의 K8s는 전부 대용량 맥락 ([네이버웹툰](https://www.bzpp.co.kr/biz/businessDetailView/BR260305A00042)) | 컨테이너 3개 이상을 롤링 배포해야 할 때. 그 전에는 k8s 매니페스트 대신 Compose blue/green과 readiness 프로브 |
| gRPC / GraphQL | 서비스 간 통신이 없음; REST + OpenAPI 계약이 쿠팡의 "강력한 계약"에 대응 | 모바일 네이티브 앱이나 BFF가 둘 이상일 때 |

## 결론

이번 조사에서 가장 뚜렷한 변화는 평가 축이 "무엇을 썼는가"에서 "무엇을 안 썼고 왜인가"로 옮겨갔다는 점이다. 2026년의 토스, 당근, 배민, 쿠팡 문구는 트레이드오프를 설명하는 능력, 테스트와 모니터링의 존재, AI 산출물을 통제한 증거를 공통으로 묻고, 회사 블로그 스스로가 Temporal 보류, ArchUnit 남용 경고, AI 의무감 사용의 비효율, 공용 DB 사고를 공개하며 절제를 성숙도로 정의한다. 그래서 여행노트에 가장 가치 있는 산출물은 코드가 아니라 ADR 여섯 건, 포스트모템 한두 건, k6 그래프 한 장, `CLAUDE.md`에 적힌 금지 동작 목록이다. 이 문서들이 있으면 Spring Modulith나 jOOQ나 MapLibre 같은 선택이 "유행"이 아니라 "결정"으로 읽히고, 없으면 같은 스택이 키워드 나열로 읽힌다.

두 번째 함의는 2026년 10월이 기준선을 올리기에 드물게 좋은 시점이라는 것이다. Spring Boot 4.1, Java 25, Kotlin 2.3, PostgreSQL 18, Next.js 16.4 Cache Components, React 19.3 View Transitions, TypeScript 7, Vitest 5가 모두 지난 12개월 안에 안정화됐고 각각 이전 세대의 OSS 지원 종료나 공식 권장 전환과 맞물려 있다. 그린필드인 여행노트는 마이그레이션 비용 없이 이 기준선에서 시작할 수 있고, 그 자체가 "버전 추적을 한다"는 신호가 된다. 다만 같은 12개월 안에 QueryDSL 유지보수 중단, App Runner 신규 중단, 카카오맵 쿼터 정책 변경, Redis 라이선스 변경처럼 "낡은 선택"이 된 것도 많으므로, 설계서의 버전과 날짜는 Renovate가 갱신하는 살아 있는 표로 두고 19 GA나 Next.js 17 같은 다음 전환점을 README에 미리 적어두는 것이 이 보고서의 권고를 6개월 뒤에도 유효하게 유지하는 방법이다.
