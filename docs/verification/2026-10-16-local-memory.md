## 메모리와 프로세스

- 1초 표본 최고 메모리는 1,664.0MiB로 공통 한도에 도달했다. 제한 도달/회수 카운터는 92,798이며 OOM, OOM-kill, 스왑 사용과 Docker 재시작은 모두 0이다. 제한 도달에는 파일 캐시 회수가 포함되므로 이 수만으로 장애라고 판단하지 않는다.
- 세 요청 구간과 복원 구간 모두 한도에 도달했다. 가장 큰 anon 표본은 복원 중 약 1,296.8MiB였다. 메모리 여유가 충분하다는 결론은 내리지 않는다.
- 10명 구간 이후 JVM NMT committed는 536.0MiB: 힙 222.9MiB와 추적된 힙 외 313.2MiB다. readiness의 힙 외는 239.6MiB였다. 384MiB 최대 힙만으로 JVM 메모리를 계산할 수 없다.
- 프로세스 RSS에는 PostgreSQL 공유 페이지가 중복되고 PostgreSQL PSS는 일반 컨테이너 권한에서 읽지 못했다. 전체 RAM 판단은 cgroup으로 한다. NMT는 RSS 전체가 아니며 reserved 주소 공간을 실제 RAM으로 합산하지 않는다.
- 현재 커널의 `memory.peak` 부재로 최고값은 1초 표본이다. 순간적인 초과 여부는 별도의 OOM/제한 도달 카운터와 함께 확인했다.
- 요청 구간의 평균 CPU는 약 1.6–1.7코어, CPU throttling은 구간별 약 63–74%의 주기에서 발생했다. 응답 시간은 이 에뮬레이션/CPU 한도의 관측값이다.
- 서비스는 종료 직전까지 모두 살아 있었다. 정상 정리 후 Docker `ExitCode=0`, `OOMKilled=false`, `RestartCount=0`, `Pid=0`이다. 이전 수동 중단 컨테이너들도 종료 상태이며 원래 개발 컨테이너는 건드리지 않았다.

## 이전 환경과의 차이

같은 1.40GB DB를 Mac 공유 디렉터리에 적재하던 실행은 1,132.8초가 걸렸고 덤프는 약 1.5MiB/s에서 수동 중단했다. 새 named volume 적재는 70.0초였고 두 전체 백업과 복원이 끝났다. API와 공통 메모리/CPU 설정, 데이터 행 수는 같으며 요청·백업 시각 계측을 보완했다. 별도 작은 쓰기 대조에서도 Mac 공유 경로의 8KiB 쓰기가 컨테이너 내부보다 약 76배 느렸다. 저장 경로 변경이 관측된 병목을 해결했지만 AWS 디스크나 native CPU의 성능 예측으로 일반화하지 않는다. 이전 DB, 부분 덤프와 기록도 보존했다.

## 판정 범위와 자료

이 합성 시나리오의 로컬 공통 메모리·부하·백업·복원 검증은 완료했다. 384MiB OS 여유분은 가정이며 실제 2GB OS/Caddy, native Linux/x86, 장시간 soak, CPU 크레딧, 운영 네트워크/TLS, SMTP/OAuth와 Vercel 쿠키 경로는 미검증이다. 큰 테이블은 임의 bytea padding이고 실제 여행 데이터 1GB의 작업 집합이나 인덱스 부하를 대체하지 않는다. 따라서 **2GB 운영 적합 확정은 하지 않는다.**

원시 결과는 로컬 실행 폴더의 `summary.json`, `analysis.json`, `container-final.json`, `run-config.json`, 요청/메모리/NMT 기록에 남긴다. 원시 DB와 덤프는 해당 실행의 named volume에 보존했다. PR에는 이 요약과 재현 소스만 포함하며 JAR, 덤프, 로그, 쿠키, 비밀값이나 개인 일정은 게시하지 않는다. 새 외부 자격증명, 운영 인증/보안 설정 또는 유료 리소스는 만들지 않았다.
