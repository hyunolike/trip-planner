# 0009. 로그인 수단: 구글과 이메일, 제공자 확장 구조

- 상태: 제안
- 날짜: 2026-10-16

## 맥락

첫 출시 로그인 수단은 구글 로그인과 이메일 가입이다(2026-10-16 결정). 카카오, 네이버, 애플은 나중에 붙인다. 이메일 가입이 들어오면 소셜 로그인만 있을 때는 없던 일이 생긴다. 비밀번호를 안전하게 저장해야 하고, 이메일 소유를 확인해야 하고, 비밀번호 재설정과 무차별 대입 방지가 필요하다. 같은 사람이 이메일로 가입한 뒤 구글로 로그인하는 경우도 처리해야 한다.

카카오 로그인을 미룬 덕분에 비즈 앱 심사와 이메일 동의 범위 문제도 출시 경로에서 빠진다.

## 결정

**데이터 구조**

- `users`는 사람이다. 이메일(대소문자 무시, 유일), 인증 시각, 닉네임, 프로필 이미지, 상태를 둔다.
- `user_identities`는 로그인 수단이다. `(provider, provider_subject)`가 유일하다. 구글은 `sub` 클레임, 이메일 가입은 `provider=password`와 사용자 ID다.
- `password_credentials`에는 비밀번호 해시만 둔다. 소셜 로그인만 쓰는 사용자는 이 행이 없다.
- `email_tokens`에는 인증과 재설정 토큰의 해시, 용도, 만료, 사용 시각을 둔다.
- 새 제공자는 Spring Security OAuth2 Client 등록과 `provider` 값 추가로 붙인다. 테이블은 바꾸지 않는다.

**이메일 가입**

- 비밀번호는 Argon2id(`Argon2PasswordEncoder`)로 해시한다. 최소 10자이고, 유출된 비밀번호 목록에 있는지 k-익명성 범위 조회로 확인한다. 조회가 실패하면 가입을 막지 않고 기록만 남긴다.
- 가입하면 미인증 상태로 만들고 인증 메일을 보낸다. 인증 링크는 24시간, 재설정 링크는 30분 유효하고 한 번만 쓸 수 있다. 토큰 원문은 메일에만 있고 DB에는 SHA-256 해시만 둔다.
- 메일 발송은 Spring Modulith 이벤트로 커밋 뒤에 한다(ADR 0002). 실패하면 이벤트 레지스트리가 다시 보낸다.
- 메일은 `spring-boot-starter-mail`의 SMTP로 보낸다. 발송 업체는 SMTP를 지원하는 트랜잭션 메일 서비스 하나를 고르고, 코드는 업체에 묶지 않는다. 발신 도메인에 SPF, DKIM, DMARC를 설정한다.
- 미인증 계정은 로그인을 거부하고 인증 메일 재발송을 안내한다.

**계정 연결**

- 구글 로그인 이메일이 이미 있는 계정과 같으면, 구글이 `email_verified=true`를 주고 기존 계정도 이메일 인증을 마친 경우에만 같은 사용자에 구글 identity를 붙인다.
- 기존 계정이 미인증이면 자동 연결하지 않는다. 누군가 남의 이메일로 먼저 가입해 두고 기다리는 계정 탈취를 막기 위해서다. 이때는 구글 쪽을 새 계정으로 만들고, 미인증 계정은 7일 뒤 정리한다.

**남용 방지와 문구**

- 로그인, 가입, 재설정 요청에 IP 기준과 이메일 기준 레이트리밋을 둔다(Valkey 버킷, ADR 0005).
- 응답 문구는 계정 존재 여부를 드러내지 않는다. 재설정 요청은 항상 "가입된 이메일이면 메일을 보냈어요"라고 답한다.
- 로그인 실패 사유는 "이메일 또는 비밀번호를 확인해 주세요" 하나로 통일한다.

## 고려한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 이메일 매직 링크만(비밀번호 없음) | 여행지에서 메일 앱을 오가야 로그인할 수 있다. 해외 로밍 환경에서 불편하다. 나중에 보조 수단으로 추가할 수 있다. |
| `users` 테이블에 `provider`, `provider_id` 열 | 한 사람이 로그인 수단을 둘 이상 가질 수 없다. 제공자를 붙일 때마다 스키마가 바뀐다. |
| BCrypt | 동작하지만 Argon2id가 메모리 비용으로 GPU 공격을 더 늦춘다. Spring Security가 둘 다 지원하므로 비용 차이가 없다. |
| Keycloak 같은 외부 인증 서버 | 운영 대상이 하나 늘어난다. 1인 운영 규모에서 Spring Security로 충분하다. |
| 이메일 일치 시 무조건 자동 연결 | 미인증 이메일 계정을 통한 계정 탈취 경로가 생긴다. |
| 패스키(WebAuthn) | 2026-10 기준 WebAuthn과 분산 세션 저장소 조합에 Spring Security 보안 공지(CVE-2026-47841)가 있었다. 수정 버전을 확인한 뒤 3단계에서 검토한다. |

## 결과

- 좋은 점: 구글 계정이 없는 사용자도 가입할 수 있다. 제공자를 붙일 때 스키마가 바뀌지 않는다. 비밀번호 저장, 토큰 해시, 계정 연결 규칙이 면접에서 설명할 보안 설계가 된다.
- 감수할 점: 메일 발송 업체와 발신 도메인 설정이 출시 전 작업에 추가된다. 비밀번호 재설정 흐름의 화면 세 개와 E2E 테스트가 늘어난다.

## 다시 볼 조건

- 카카오나 네이버를 붙일 때 이메일 동의 범위와 심사 일정을 확인하고, 이메일을 받지 못하는 제공자의 계정 연결 규칙을 새 ADR로 정한다.
- 패스키 보안 공지의 수정 버전이 나오면 보조 로그인 수단으로 검토한다.

## 확인 필요

- 트랜잭션 메일 업체의 2026년 무료 한도와 한국 메일함(네이버, 다음) 도달률.
- 유출 비밀번호 범위 조회 API의 이용 조건.
