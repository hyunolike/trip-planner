# 0002. Spring Modulith 모듈러 모놀리스, Kafka 없이 아웃박스

- 상태: 제안
- 날짜: 2026-10-16

## 맥락

API 하나가 인증, 여행 편집, 공유와 복제, 완료 체크, 날씨를 맡는다. 배포 단위는 하나이고 운영자도 한 명이다. 그래도 경계는 필요하다. 공유 링크로 여행을 복제할 때 원본 여행의 내부 구조에 share 모듈이 직접 손대면 나중에 분리할 수 없다.

모듈 사이에는 비동기로 처리할 일이 몇 가지 있다. 여행을 복제하면 복제 통계를 남기고, 탈퇴하면 토큰 revoke와 이미지 삭제가 따라온다. 이 일들은 트랜잭션이 커밋된 뒤에 실행되어야 하고, 실패하면 다시 시도되어야 한다.

## 결정

- Spring Modulith 2.1로 `auth`, `trip`, `share`, `progress`, `weather` 모듈을 나눈다. 모듈은 최상위 패키지 하나이고, 다른 모듈은 공개 API 패키지만 참조한다.
- `ApplicationModules.of(...).verify()` 테스트로 모듈 간 금지 의존을 빌드에서 잡는다.
- 모듈 간 비동기 처리는 Modulith의 JDBC 이벤트 퍼블리케이션 레지스트리로 한다. 이벤트는 같은 트랜잭션 안에 기록되고, 커밋 뒤 리스너가 처리하며, 실패한 이벤트는 재시작 시 다시 전송된다. 이것이 아웃박스 패턴이다.
- 별도 ArchUnit 규칙은 3~5개로 제한한다. Modulith가 이미 내부적으로 ArchUnit을 쓴다.

## 고려한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 마이크로서비스 | 서비스 간 트랜잭션과 데이터 일관성 문제만 늘어난다. 1인 운영으로 감당할 이유가 없다. |
| Kafka 또는 RabbitMQ | 외부 소비자가 없고 토픽이 하나다. 브로커 운영 부담에 비해 얻는 것이 없다. 면접에서 "왜 Kafka인가"에 답할 문제가 없다. |
| 모듈 구분 없는 단일 패키지 | 복제와 권한 로직이 여행 엔티티 내부를 직접 건드리게 된다. 나중에 분리하려면 다시 짜야 한다. |
| Temporal 같은 워크플로 엔진 | 장기 실행 작업이 없다. 우아한형제들도 같은 이유로 도입을 보류했다. |

## 결과

- 좋은 점: 경계가 테스트로 강제되고, 이벤트 재전송이 보장된다. 분리가 필요해지면 share 모듈부터 떼어낼 수 있다.
- 감수할 점: 이벤트 레지스트리 테이블을 운영하고, 오래된 완료 이벤트를 주기적으로 정리해야 한다.

## 다시 볼 조건

- 알림 서비스나 분석 파이프라인처럼 API 밖에서 이벤트를 소비하는 곳이 생기면 Modulith의 이벤트 외부화로 브로커를 붙인다.
