# 0004. PostgreSQL 18과 PostGIS

- 상태: 제안
- 날짜: 2026-10-16

## 맥락

스톱마다 좌표가 있고, 하루 동선은 좌표의 순서다. 앞으로 "숙소에서 10분 거리의 식당"이나 "오늘 동선과 가까운 장소" 같은 조회가 필요하다. 가이드 본문은 블록 구조가 자주 바뀐다. 한국 대기업 공고는 대부분 MySQL을 쓰지만, 평가는 DB 종류보다 설계와 운영 증거를 본다.

## 결정

- PostgreSQL 18(최신 마이너 18.6)과 PostGIS 3.6을 쓴다. 운영 DB는 Supabase 서울 리전이다.
- 기본 키는 `uuidv7()`로 만든다. 시간순으로 정렬되어 B-tree 지역성이 좋다. 생성 시각이 드러나므로 공유 링크에는 별도의 32바이트 랜덤 토큰을 쓴다.
- 스톱 좌표는 `geography(Point, 4326)` 생성 컬럼과 GiST 인덱스로 둔다. 하루 동선은 `geography(LineString)`으로 저장한다.
- jsonb는 가이드 블록 본문과 스톱의 이동 경유지처럼 조회 조건으로 쓰지 않는 데이터에만 쓴다. 필터링하는 값은 일반 컬럼으로 올린다.
- 생성 컬럼은 `STORED`를 명시한다. PostgreSQL 18부터 생성 컬럼의 기본값이 가상 컬럼이다.

## 고려한 대안

| 대안 | 기각 이유 |
| --- | --- |
| MySQL 8 | 공간 쿼리와 지리 좌표계 지원이 PostGIS보다 약하다. jsonb에 해당하는 인덱싱 선택지도 적다. |
| 좌표를 위도·경도 두 컬럼으로 저장 | 거리 계산과 반경 조회를 애플리케이션에서 해야 한다. 인덱스를 쓸 수 없다. |
| Neon | 아시아 리전이 싱가포르뿐이라 한국에서 왕복 약 200ms다. PR 미리보기 브랜치 용도로만 고려한다. |
| pgvector 지금 도입 | 장소 임베딩 테이블이 없어 설명할 문제가 없다. |

## 결과

- 좋은 점: 반경 조회와 동선 거리를 SQL로 계산한다. 기존 오사카·교토 샘플의 좌표와 경유지를 그대로 옮길 수 있다.
- 감수할 점: Testcontainers에 PostGIS 이미지를 써야 한다. 한국 공고와 다른 DB라는 점은 이 ADR로 설명한다.

## 다시 볼 조건
